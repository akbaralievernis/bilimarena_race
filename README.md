# Bilim Arena Race

Образовательная многопользовательская гонка. Учитель запускает соревнование, команды
подключаются со своих устройств и продвигаются по карте, проходя учебные испытания.
Общий экран показывает карту и положение команд в реальном времени, а после финиша —
результаты и аналитику.

> Статус: **Этап 4** — аккаунты, комнаты, команды и лобби (Этап 1), маршрут и карта
> гонки (Этап 2), учебные задания на чекпоинтах с проверкой ответа на сервере (Этап 3),
> очки, пауза после неверного ответа, места и итоговая таблица (Этап 4).
> Это самостоятельный проект: он не использует код, базу данных, API и авторизацию
> основного сайта Bilim Arena. Интеграция возможна только после завершения
> и тестирования standalone-версии.

## Основная идея

1. **Учитель создаёт гонку:** выбирает тему, настраивает маршрут и испытания, открывает комнату.
2. **Студенты подключаются** по коду комнаты с телефонов, планшетов или ноутбуков и
   объединяются в команды.
3. **Гонка:** на каждом чекпоинте команду ждёт испытание. Правильные и быстрые решения
   продвигают команду по карте.
4. **Общий экран** показывает карту и позиции команд в реальном времени.
5. **Финиш:** итоговая таблица и образовательная аналитика — какие темы даются легко,
   а что стоит повторить.

Все критические решения (очки, позиции, победитель, завершение гонки, награды) принимает
сервер, а не браузер. Подробнее — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Что уже работает (Этап 1)

- Учитель: регистрация и вход по email/паролю, выход, сохранение сессии.
- Создание гонки: название, описание, серверный код комнаты вида `A7K9Q2`.
- Студент: вход без регистрации — код комнаты и имя (анонимная сессия Supabase).
- Лобби учителя: код с копированием кода и ссылки, команды (создать, переименовать,
  удалить пустую), распределение студентов, «Начать гонку» и «Завершить гонку».
- Лобби студента: имя, команда и сокомандники, ожидание старта.
- Realtime: новые участники, команды, распределение и статус гонки обновляются у всех
  без перезагрузки; при обрыве связи — сообщение и автоматическое восстановление.
- Row Level Security и доверенные Postgres-функции: браузер не может сам изменить гонку,
  участника или команду.

## Этап 2: карта гонки

- **Route / Checkpoints:** при создании гонки учитель задаёт маршрут из 1–20 чекпоинтов
  (добавить, переименовать, поменять порядок ↑ ↓, удалить). Маршрут: Старт →
  чекпоинты → Финиш; позиции назначает база, после создания маршрут не меняется.
- **Team Position:** каждая команда стоит на точке маршрута (0 = Старт). Студент нажимает
  «Пройти чекпоинт N» — сервер пропускает только следующий шаг, только во время гонки
  и только для своей команды.
- **Race Map:** экран `/race/[raceId]` — у учителя карта и прогресс всех команд, у студента
  «Сейчас / Дальше», кнопка хода и карта с подсветкой своей команды. При старте лобби
  само переводит всех на карту.
- **Realtime Movement:** ход команды сразу виден учителю и другим студентам без
  перезагрузки (тот же канал `race:<id>`, что и в лобби).

Подробности модели и защиты — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md#этап-2-карта-маршрут-чекпоинты).
Миграции Этапа 2 применяются той же командой `npx supabase db push`.

## Этап 3: задания на чекпоинтах

- **Учитель** на `/create` задаёт для каждого чекпоинта задание: «Выбор ответа»
  (2–6 вариантов, отмечается правильный) или «Короткий ответ» (правильный ответ; регистр,
  пробелы и ё/е не важны). Всё проверяется на сервере и ещё раз в базе.
- **Студент** на карте гонки видит задание следующего чекпоинта своей команды, отвечает
  кнопкой «Ответить». Правильный ответ сразу переводит команду дальше (после последнего —
  на Финиш), неправильный оставляет на месте. Повторная отправка не даёт двойного хода.
- **Правильные ответы** хранятся в закрытой схеме базы и никогда не уходят в браузер,
  API-ответы или Realtime.
- **Учитель** видит по каждой команде позицию, пройденные чекпоинты, число правильных и
  неправильных ответов и время финиша — обновляется без перезагрузки.
- Гонки без заданий (созданные до Этапа 3) работают как раньше — кнопкой.

Миграции Этапа 3 применяются командой `npx supabase db push`.

## Этап 4: очки и рейтинг

- **Очки за ответ:** верный — 100 + бонус за скорость до 50 (−1 очко за каждые 3 секунды с
  момента, когда команда пришла на текущую точку; на старте — с начала гонки); неверный —
  −20. Счёт команды не опускается ниже нуля.
- **Пауза 10 секунд** после неверного ответа: вся команда ждёт, прежде чем ответить на то же
  задание снова. Перебрать варианты подряд нельзя — сервер отвечает `answer_cooldown`,
  попытка не записывается. У студента — обратный отсчёт на кнопке.
- **Финиш:** первые три команды получают +100, +60 и +30.
- **Места:** сначала финишировавшие (кто раньше), затем по позиции на карте, при равенстве —
  по очкам; одинаковые команды делят место.
- **Учитель** видит команды по местам: очки, позиция, верные и неверные ответы, точность.
  **Студент** — очки и место своей команды и общую таблицу. После «Завершить гонку» у всех
  появляются **итоги гонки**.
- Очки и места считает только база (`submit_answer`, `private.team_standings`); у каждого
  ответа записаны его очки, поэтому два одновременных финиша не делят один бонус, а
  записать очки или обойти паузу из браузера нельзя.
- Ответы гонок Этапа 3 при обновлении получают базовые очки (100 / −20, без бонуса за скорость).

Миграции Этапа 4 применяются командой `npx supabase db push`.

## Planned features

- **Комнаты** — вход по коду, лобби перед стартом. *(готово на Этапе 1)*
- **Команды** — создание команд и распределение участников. *(готово на Этапе 1)*
- **Карта** — маршрут с чекпоинтами, общий экран с позициями команд. *(готово на Этапе 2)*
- **Задания** — быстрые вопросы, задачи, программирование, исправление ошибок в коде,
  скоростная печать, сборка понятий, пазлы, командные задания. *(Этап 3: выбор ответа и
  короткий ответ)*
- **Мини-игры** — отдельные интерактивные испытания на чекпоинтах.
- **Realtime** — мгновенное обновление карты и счёта у всех участников. *(основа — Этап 1)*
- **Очки и рейтинг** — очки за ответы и скорость, места, итоговая таблица. *(готово на Этапе 4)*
- **Бонусы** — ускорения и особые чекпоинты.
- **Стратегия** — выбор маршрута и момента для бонусов.
- **Результаты** — история гонки по ходам и ответам. *(итоговая таблица — Этап 4)*
- **Аналитика** — разбор ответов по темам и заданиям для учителя.

## Installation

Требуется **Node.js 24+** и npm.

```bash
git clone https://github.com/akbaralievernis/bilimarena_race.git
cd bilimarena_race
npm install
```

Стартовая страница работает и без Supabase. Для входа, создания гонок и лобби нужен
Supabase-проект — настройка ниже.

## Настройка Supabase

Для гонки нужен **отдельный** Supabase-проект — не проект основного сайта Bilim Arena.

### 1. Создайте проект

[supabase.com/dashboard](https://supabase.com/dashboard) → **New project**. Запомните
пароль базы данных — он понадобится для `db push` (в репозиторий его не добавлять).

### 2. Добавьте переменные окружения

```bash
cp .env.example .env.local
```

Заполните в `.env.local` (Dashboard → **Project Settings → API Keys** и **Data API**):

| Переменная | Где используется | Описание |
| --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | браузер и сервер | URL проекта, `https://<project-ref>.supabase.co` |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | браузер и сервер | Publishable key (`sb_publishable_...`) или legacy anon key. Публичный по назначению: доступ к данным защищают RLS и функции базы |
| `SUPABASE_SECRET_KEY` | — | **Не используется.** Никогда не добавляйте префикс `NEXT_PUBLIC_` к секретным ключам |

`.env.local` исключён из Git.

### 3. Примените миграции

Миграции лежат в [`supabase/migrations/`](supabase/migrations) и полностью воссоздают схему:
таблицы, ограничения, RLS, функции и Realtime.

```bash
npx supabase login
npx supabase link --project-ref <project-ref>
npx supabase db push
```

`link` и `db push` спросят пароль базы данных. Проверить, что применено:
`npx supabase migration list`.

### 4. Настройте Auth

Dashboard → **Authentication**:

- **Sign In / Providers → Anonymous Sign-Ins** — включить (иначе студенты не смогут войти).
- **Sign In / Providers → Email** — включён, **«Confirm email» оставьте включённым**:
  учитель подтверждает адрес по ссылке из письма (её обрабатывает `/auth/confirm`).
  Для тестов его отключать не нужно — см. «Интеграционные тесты».
- **URL Configuration** — Site URL `http://localhost:3000` (для разработки) и домен Vercel
  после деплоя; в Redirect URLs добавьте `http://localhost:3000/**` и
  `https://<ваш-домен>/**`.
- Для продакшена рекомендуется включить CAPTCHA (Attack Protection): анонимный вход
  доступен всем, у кого открыт сайт.

Realtime дополнительно настраивать не нужно: миграции создают политики для приватных
каналов. Для строгости можно отключить **Realtime Settings → Allow public access**.

### 5. Запустите проект

```bash
npm run dev
```

Откройте <http://localhost:3000>.

### 6. Создайте аккаунт учителя

`/login` → вкладка **Регистрация**: имя, email, пароль (от 8 символов). Либо Dashboard →
**Authentication → Users → Add user** (отметьте «Auto Confirm User»), затем вход на `/login`.

### 7. Проверьте создание и подключение

1. Учитель: **Создать гонку** → название → откроется лобби с кодом комнаты.
2. В другом браузере или окне инкогнито: **Подключиться к гонке** → код и имя.
3. Студент появится у учителя без перезагрузки. Создайте команду, назначьте в неё
   студента — изменение сразу появится у студента.
4. **Начать гонку** — статус сменится у всех подключённых.

### Локальный Supabase (альтернатива)

С установленным Docker можно поднять Supabase локально — конфигурация уже в
[`supabase/config.toml`](supabase/config.toml) (анонимный вход включён, подтверждение
email выключено):

```bash
npx supabase start          # применит миграции, выведет URL и ключи для .env.local
npx supabase db reset       # пересоздать базу из миграций
```

## Development

```bash
npm run dev                 # сервер разработки
npm run lint                # ESLint
npm run typecheck           # генерация типов маршрутов + tsc
npm run test                # unit-тесты и тесты базы (PGlite, без Supabase)
npm run check               # всё выше вместе
npm run test:integration    # сценарии против настоящего Supabase (см. ниже)
```

`npm run test` применяет все миграции к встроенному PostgreSQL и проверяет RLS и функции
от имени ролей `authenticated` / `anon` — так же, как запросы приходят через Supabase API.

### Интеграционные тесты

`npm run test:integration` проверяет создание гонки, подключение, команды, старт,
доставку Realtime и запрет прямых записей на настоящем dev-проекте Supabase.
Тесты **не регистрируют пользователей по email** и не отправляют писем:

- **Учитель** — один заранее созданный тестовый аккаунт. Создайте его один раз:
  Dashboard → **Authentication → Users → Add user → Create new user**, включите
  **Auto Confirm User** (письмо не отправляется). Затем:

  ```bash
  cp .env.test.example .env.test.local
  ```

  и впишите `TEST_TEACHER_EMAIL` / `TEST_TEACHER_PASSWORD`. Файл исключён из Git и читается
  только конфигом интеграционных тестов — приложение его не загружает.
- **Студенты** — 3 анонимных пользователя за прогон (нужен включённый Anonymous Sign-Ins).
- Каждый прогон создаёт свою гонку и в конце завершает её.

Почему не `signUp`: при включённом «Confirm email» каждая регистрация отправляет письмо —
у встроенной почты Supabase очень низкий лимит (`email rate limit exceeded`), письма на
несуществующие адреса возвращаются, и Supabase может ограничить проекту отправку почты.
А сессии до подтверждения всё равно нет.

Лимиты Supabase Auth считаются по IP (по умолчанию около 30 анонимных входов в час),
поэтому частые прогоны подряд могут упереться в `over_request_rate_limit` — тесты в этом
случае не повторяют запросы, а сообщают, что нужно подождать. Анонимные пользователи
копятся в `auth.users`; при необходимости удаляйте старых в SQL Editor:
`delete from auth.users where is_anonymous and created_at < now() - interval '7 days';`
(их места в гонках удаляются каскадом).

## Deployment

Проект готов к деплою на [Vercel](https://vercel.com) без дополнительной конфигурации:

1. Импортируйте репозиторий в Vercel — фреймворк Next.js определится автоматически.
2. В **Project Settings → Environment Variables** добавьте `NEXT_PUBLIC_SUPABASE_URL`
   и `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (отдельно для Production и Preview, если нужны
   разные Supabase-проекты).
3. Значения `NEXT_PUBLIC_*` встраиваются в сборку, поэтому после их изменения
   нужен повторный деплой.
4. Добавьте домен Vercel в **Supabase → Authentication → URL Configuration**
   (Site URL и Redirect URLs).
