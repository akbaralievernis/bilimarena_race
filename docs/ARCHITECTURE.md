# Архитектура Bilim Arena Race

Состояние: **Этап 1** — Supabase, Auth, комнаты, команды, участники, лобби и Realtime.
Игровой механики (карта, задания, очки) пока нет.

## Главный принцип

**Браузер отправляет только намерения, решения принимает база.**
Клиент может попросить «подключи меня к гонке A7K9Q2» или «начни гонку», но не может
сам записать участника, выбрать код комнаты или поменять статус. Каждая такая операция —
Postgres-функция, которая проверяет, кто её вызывает.

```text
Браузер ──► Server Action (Next.js) ──► RPC-функция в Postgres ──► таблицы
               валидация ввода,          проверка прав, статуса,     RLS: прямая
               понятные ошибки           атомарная запись             запись закрыта
```

Server Actions — удобный слой для форм и сообщений. Безопасность от него не зависит:
даже если вызвать RPC напрямую из браузера, функция выполнит те же проверки.

## Auth

| Роль | Как входит | Что это в Supabase |
| --- | --- | --- |
| Учитель | Email + пароль (`/login`: вход и регистрация) | Обычный пользователь Supabase Auth |
| Студент | Код комнаты + имя (`/join`), без регистрации | Анонимный пользователь (`signInAnonymously`), JWT с `is_anonymous = true` |

- **Учитель — это любой не анонимный пользователь.** `create_race()` отклоняет анонимные
  сессии (`teacher_account_required`). Роль в конкретной гонке определяется владением
  (`races.created_by`), а не полем, которое мог бы изменить клиент.
- **Сессия хранится в cookies** (`@supabase/ssr`). `proxy.ts` (бывший middleware) обновляет
  токены перед рендером страниц `/login`, `/create`, `/join`, `/race/*`, `/auth/*`;
  главная страница остаётся статической.
- **На сервере личность проверяется через `getClaims()`** (проверка подписи JWT), а не
  через `getSession()`.
- Анонимная сессия переживает перезагрузку страницы: повторное подключение с того же
  устройства возвращает то же место в гонке.
- Подтверждение email (если включено в проекте) обрабатывает `/auth/confirm`.

## Сущности базы данных

Миграции: [`supabase/migrations/`](../supabase/migrations).

```text
auth.users ─┬─< races (created_by)          on delete cascade
            └─< participants (user_id)      on delete cascade

races ─┬─< teams (race_id)                  on delete cascade
       └─< participants (race_id)           on delete cascade

teams ─< participants (race_id, team_id)    составной FK: команда из той же гонки,
                                            on delete set null (team_id)
```

| Таблица | Ключевые поля и ограничения |
| --- | --- |
| `races` | `code` UNIQUE, формат `^[23456789A-HJ-NP-Z]{6}$`; `title` 3–80; `description` ≤ 500; `status` enum `draft / lobby / running / finished`; `created_by`; `started_at`, `finished_at` |
| `teams` | `race_id`; `name` 1–40, уникально в гонке без учёта регистра; не больше 20 команд |
| `participants` | `race_id`, `user_id` — UNIQUE (одно место на пользователя в гонке); `display_name` 2–30, уникально среди студентов гонки без учёта регистра; `role` enum `teacher / student`; `team_id` только у студентов |

Триггеры целостности:
- `code` и `created_by` гонки неизменяемы (`immutable_field`);
- статус меняется только по разрешённым переходам (`private.can_transition`), даже при
  прямом `UPDATE` с правами администратора:

```text
draft → lobby → running → finished
          └──────────────────┘ (гонку можно закрыть из лобби)
```

## Модель RLS

Для всех трёх таблиц RLS включён, у ролей `anon` и `authenticated` отозваны права на
`INSERT / UPDATE / DELETE`, политик на запись нет. Внутренние id пользователей
(`races.created_by`, `participants.user_id`) клиентам не выдаются даже на чтение
(права на уровне столбцов).

| Таблица | SELECT | INSERT | UPDATE | DELETE |
| --- | --- | --- | --- | --- |
| `races` | владелец и участники гонки | только `create_race()` | только `start_race()` / `finish_race()` | нет |
| `teams` | владелец и участники гонки | только `create_team()` | только `rename_team()` | только `delete_team()` (пустая команда) |
| `participants` | владелец видит всех; студент — себя и своих сокомандников | `create_race()` (учитель), `join_race()` (студент) | только `assign_participant()` | каскадом при удалении гонки/пользователя |

Запросы без сессии (`anon`) не могут ни читать таблицы, ни вызывать функции.

Вспомогательные функции для политик (`private.is_race_owner`, `is_race_participant`,
`my_team_id`) — `security definer` в схеме `private`, которая не опубликована в Data API.

## Доверенные операции

Все — `security definer`, `search_path = ''`, выполнение разрешено только роли
`authenticated`. Ошибки — SQLSTATE `P0001` со стабильным кодом в `message`
(`race_not_found`, `race_finished`, …); тексты для UI — в [`lib/race/errors.ts`](../lib/race/errors.ts).

| Функция | Кто может | Что проверяет |
| --- | --- | --- |
| `create_race(title, description)` | учитель (не анонимный) | ввод; ≤ 50 незавершённых гонок; сам генерирует код; ставит `lobby`; добавляет учителя участником |
| `join_race(code, display_name)` | любой вошедший | код существует; гонка не `finished` и не `draft`; имя свободно; ≤ 200 студентов; повторный вход возвращает то же место |
| `create_team`, `rename_team`, `delete_team` | владелец гонки | гонка не завершена; имя уникально; удалить можно только пустую |
| `assign_participant(participant, team \| null)` | владелец гонки | участник — студент этой гонки; команда из этой же гонки |
| `start_race`, `finish_race` | владелец гонки | допустимый переход статуса |
| `get_lobby(race_id)` | владелец и участники | возвращает снимок лобби без внутренних id; студенту — только его команду |
| `list_my_races()` | учитель | только свои гонки |

Для чужой или несуществующей гонки ответ одинаковый (`race_not_found`), чтобы по ответам
нельзя было перебирать id. Строки гонки блокируются (`FOR UPDATE`) на время изменения.

## Генерация кода комнаты

- 6 символов из 32: `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` — без `0/O` и `1/I`;
  32⁶ ≈ 1,07 млрд комбинаций.
- Генерируется **в базе** (`private.generate_room_code`) из байтов `gen_random_uuid()`
  (криптостойкий генератор). 256 делится на 32, поэтому все символы равновероятны.
- Уникальность гарантирует `UNIQUE (code)`; при коллизии `create_race()` просто пробует
  снова. Клиент код не передаёт вообще.
- Ввод нормализуется: регистр, пробелы и дефисы, кириллические двойники из русской
  раскладки (`А7К9Q2` → `A7K9Q2`) — одинаково в TypeScript и в SQL.

## Модель Realtime

- Канал на гонку: **приватный Broadcast `race:<race_id>`**.
- Триггеры на `races`, `teams`, `participants` вызывают `realtime.send()` с сигналом
  `lobby_changed` и полезной нагрузкой только вида `{ table, op }` — без данных.
  Сервер Realtime добавляет к ней служебный `id` сообщения; это не id строки базы.
- Клиент по сигналу перечитывает снимок через `get_lobby()` — права применяет база,
  по сокету ничего лишнего не передаётся.
- Подписаться может только владелец или участник гонки: политика на `realtime.messages`
  проверяет топик через `private.can_access_race_topic()`. Политики на запись в канал нет —
  браузер не может подделать событие.
- Устойчивость ([`components/lobby/use-lobby.ts`](../components/lobby/use-lobby.ts)):
  после (пере)подключения — перечитывание снимка; при потере связи — баннер
  «Соединение с гонкой потеряно» и опрос каждые 10 с; при возвращении на вкладку —
  перечитывание. Запросы идут строго по одному, ответы не могут прийти не по порядку.

Почему Broadcast, а не Postgres Changes: события удаления в Postgres Changes нельзя
отфильтровать по гонке, а Broadcast из базы — рекомендуемый Supabase способ для
масштабирования и приватных каналов.

## Сценарии

**Учитель:** `/login` → `/create` (название, описание) → `create_race()` → `/race/<id>/lobby`:
код комнаты с копированием кода и ссылки `/join?code=…`, команды (создать,
переименовать, удалить пустую), участники с выбором команды, «Начать гонку»
(подтверждение) → `running`, затем «Завершить гонку» → `finished`.

**Студент:** `/join` (код, имя) → анонимная сессия (на сервере) → `join_race()` →
`/race/<id>/lobby`: «Ты подключён как», команда и сокомандники или «Команда пока не
назначена», «Ожидаем начала гонки…». Все изменения приходят без перезагрузки.

## Границы безопасности

| Граница | Что защищает |
| --- | --- |
| Postgres-функции | Все решения о правах и состоянии гонки |
| RLS и права на столбцы | Прямой доступ через Data API: чтение только своего, запись запрещена |
| Триггеры и ограничения | Целостность даже при ошибке в коде функций или ручной правке |
| Приватный Realtime-канал | Получать события — только участникам, отправлять — только базе |
| Server Actions | Валидация ввода и понятные сообщения; повторно проверяют типы аргументов |
| `proxy.ts` / `getClaims()` | Актуальная и проверенная сессия на сервере |
| `safeNextPath()` | Редирект после входа только на пути этого сайта |

Секретный ключ Supabase приложению не нужен и нигде не используется.

## Тесты

- `tests/db/*` — миграции применяются к настоящему PostgreSQL (PGlite) с имитацией ролей
  Supabase ([`tests/db/supabase-shim.sql`](../tests/db/supabase-shim.sql)); атаки выполняются
  от ролей `authenticated` / `anon` с JWT-claims, как это делает PostgREST.
- `tests/*.test.ts` — валидация, статусы, ошибки, разбор снимка лобби.
- `tests/integration/*` — сценарии против настоящего Supabase-проекта, включая доставку
  Realtime (`npm run test:integration`). Учитель — заранее созданный подтверждённый
  тестовый аккаунт из `.env.test.local`, студенты — анонимные; регистраций по email и
  секретного ключа нет.
