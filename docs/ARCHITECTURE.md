# Архитектура Bilim Arena Race

Состояние: **Этап 3** — поверх Этапа 1 (Supabase, Auth, комнаты, команды, участники,
лобби, Realtime) и Этапа 2 (маршрут, чекпоинты, позиции, карта) добавлены учебные
задания: чекпоинт проходится только правильным ответом, проверенным сервером
(см. [Этап 3](#этап-3-учебные-задания-на-чекпоинтах)). Очков и рейтинга пока нет.

## Главный принцип

**Браузер отправляет только намерения, решения принимает база.**
Клиент может попросить «подключи меня к гонке A7K9Q2» или «начни гонку», но не может
сам записать участника, выбрать код комнаты или поменять статус. Каждая такая операция —
Postgres-функция, которая проверяет, кто её вызывает.

```text
Браузер ──► Server Action (Next.js) ──► RPC-функция в Postgres ──► таблицы
               валидация ввода,          проверка прав, статуса,     RLS: прямая
               понятные ошибки           атомарная запись             запись закрыта
```

Server Actions — удобный слой для форм и сообщений. Безопасность от него не зависит:
даже если вызвать RPC напрямую из браузера, функция выполнит те же проверки.

## Auth

| Роль | Как входит | Что это в Supabase |
| --- | --- | --- |
| Учитель | Email + пароль (`/login`: вход и регистрация) | Обычный пользователь Supabase Auth |
| Студент | Код комнаты + имя (`/join`), без регистрации | Анонимный пользователь (`signInAnonymously`), JWT с `is_anonymous = true` |

- **Учитель — это любой не анонимный пользователь.** `create_race()` отклоняет анонимные
  сессии (`teacher_account_required`). Роль в конкретной гонке определяется владением
  (`races.created_by`), а не полем, которое мог бы изменить клиент.
- **Сессия хранится в cookies** (`@supabase/ssr`). `proxy.ts` (бывший middleware) обновляет
  токены перед рендером страниц `/login`, `/create`, `/join`, `/race/*`, `/auth/*`;
  главная страница остаётся статической.
- **На сервере личность проверяется через `getClaims()`** (проверка подписи JWT), а не
  через `getSession()`.
- Анонимная сессия переживает перезагрузку страницы: повторное подключение с того же
  устройства возвращает то же место в гонке.
- Подтверждение email (если включено в проекте) обрабатывает `/auth/confirm`.

## Сущности базы данных

Миграции: [`supabase/migrations/`](../supabase/migrations).

```text
auth.users ─┬─< races (created_by)          on delete cascade
            └─< participants (user_id)      on delete cascade

races ─┬─< teams (race_id)                  on delete cascade
       └─< participants (race_id)           on delete cascade

teams ─< participants (race_id, team_id)    составной FK: команда из той же гонки,
                                            on delete set null (team_id)
```

| Таблица | Ключевые поля и ограничения |
| --- | --- |
| `races` | `code` UNIQUE, формат `^[23456789A-HJ-NP-Z]{6}$`; `title` 3–80; `description` ≤ 500; `status` enum `draft / lobby / running / finished`; `created_by`; `started_at`, `finished_at` |
| `teams` | `race_id`; `name` 1–40, уникально в гонке без учёта регистра; не больше 20 команд |
| `participants` | `race_id`, `user_id` — UNIQUE (одно место на пользователя в гонке); `display_name` 2–30, уникально среди студентов гонки без учёта регистра; `role` enum `teacher / student`; `team_id` только у студентов |

Триггеры целостности:
- `code` и `created_by` гонки неизменяемы (`immutable_field`);
- статус меняется только по разрешённым переходам (`private.can_transition`), даже при
  прямом `UPDATE` с правами администратора:

```text
draft → lobby → running → finished
          └──────────────────┘ (гонку можно закрыть из лобби)
```

## Модель RLS

Для всех трёх таблиц RLS включён, у ролей `anon` и `authenticated` отозваны права на
`INSERT / UPDATE / DELETE`, политик на запись нет. Внутренние id пользователей
(`races.created_by`, `participants.user_id`) клиентам не выдаются даже на чтение
(права на уровне столбцов).

| Таблица | SELECT | INSERT | UPDATE | DELETE |
| --- | --- | --- | --- | --- |
| `races` | владелец и участники гонки | только `create_race()` | только `start_race()` / `finish_race()` | нет |
| `teams` | владелец и участники гонки | только `create_team()` | только `rename_team()` | только `delete_team()` (пустая команда) |
| `participants` | владелец видит всех; студент — себя и своих сокомандников | `create_race()` (учитель), `join_race()` (студент) | только `assign_participant()` | каскадом при удалении гонки/пользователя |

Запросы без сессии (`anon`) не могут ни читать таблицы, ни вызывать функции.

Вспомогательные функции для политик (`private.is_race_owner`, `is_race_participant`,
`my_team_id`) — `security definer` в схеме `private`, которая не опубликована в Data API.

## Доверенные операции

Все — `security definer`, `search_path = ''`, выполнение разрешено только роли
`authenticated`. Ошибки — SQLSTATE `P0001` со стабильным кодом в `message`
(`race_not_found`, `race_finished`, …); тексты для UI — в [`lib/race/errors.ts`](../lib/race/errors.ts).

| Функция | Кто может | Что проверяет |
| --- | --- | --- |
| `create_race(title, description)` | учитель (не анонимный) | ввод; ≤ 50 незавершённых гонок; сам генерирует код; ставит `lobby`; добавляет учителя участником |
| `join_race(code, display_name)` | любой вошедший | код существует; гонка не `finished` и не `draft`; имя свободно; ≤ 200 студентов; повторный вход возвращает то же место |
| `create_team`, `rename_team`, `delete_team` | владелец гонки | гонка не завершена; имя уникально; удалить можно только пустую |
| `assign_participant(participant, team \| null)` | владелец гонки | участник — студент этой гонки; команда из этой же гонки |
| `start_race`, `finish_race` | владелец гонки | допустимый переход статуса |
| `get_lobby(race_id)` | владелец и участники | возвращает снимок лобби без внутренних id; студенту — только его команду |
| `list_my_races()` | учитель | только свои гонки |

Для чужой или несуществующей гонки ответ одинаковый (`race_not_found`), чтобы по ответам
нельзя было перебирать id. Строки гонки блокируются (`FOR UPDATE`) на время изменения.

## Генерация кода комнаты

- 6 символов из 32: `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` — без `0/O` и `1/I`;
  32⁶ ≈ 1,07 млрд комбинаций.
- Генерируется **в базе** (`private.generate_room_code`) из байтов `gen_random_uuid()`
  (криптостойкий генератор). 256 делится на 32, поэтому все символы равновероятны.
- Уникальность гарантирует `UNIQUE (code)`; при коллизии `create_race()` просто пробует
  снова. Клиент код не передаёт вообще.
- Ввод нормализуется: регистр, пробелы и дефисы, кириллические двойники из русской
  раскладки (`А7К9Q2` → `A7K9Q2`) — одинаково в TypeScript и в SQL.

## Модель Realtime

- Канал на гонку: **приватный Broadcast `race:<race_id>`**.
- Триггеры на `races`, `teams`, `participants` вызывают `realtime.send()` с сигналом
  `lobby_changed` и полезной нагрузкой только вида `{ table, op }` — без данных.
  Сервер Realtime добавляет к ней служебный `id` сообщения; это не id строки базы.
- Клиент по сигналу перечитывает снимок через `get_lobby()` — права применяет база,
  по сокету ничего лишнего не передаётся.
- Подписаться может только владелец или участник гонки: политика на `realtime.messages`
  проверяет топик через `private.can_access_race_topic()`. Политики на запись в канал нет —
  браузер не может подделать событие.
- Устойчивость ([`components/lobby/use-lobby.ts`](../components/lobby/use-lobby.ts)):
  после (пере)подключения — перечитывание снимка; при потере связи — баннер
  «Соединение с гонкой потеряно» и опрос каждые 10 с; при возвращении на вкладку —
  перечитывание. Пока гонка идёт, открытая вкладка ещё и перечитывает снимок раз в
  20–25 с (случайный сдвиг, чтобы класс не опрашивал сервер одновременно): сигнал может
  потеряться и при живом сокете, а карта и таблица мест не должны «застыть».
  Запросы идут строго по одному, ответы не могут прийти не по порядку.

Почему Broadcast, а не Postgres Changes: события удаления в Postgres Changes нельзя
отфильтровать по гонке, а Broadcast из базы — рекомендуемый Supabase способ для
масштабирования и приватных каналов.

## Сценарии

**Учитель:** `/login` → `/create` (название, описание) → `create_race()` → `/race/<id>/lobby`:
код комнаты с копированием кода и ссылки `/join?code=…`, команды (создать,
переименовать, удалить пустую), участники с выбором команды, «Начать гонку»
(подтверждение) → `running`, затем «Завершить гонку» → `finished`.

**Студент:** `/join` (код, имя) → анонимная сессия (на сервере) → `join_race()` →
`/race/<id>/lobby`: «Ты подключён как», команда и сокомандники или «Команда пока не
назначена», «Ожидаем начала гонки…». Все изменения приходят без перезагрузки.

## Этап 2: карта, маршрут, чекпоинты

Миграции `20260928100000_race_route.sql` (схема) и `20260928100100_race_route_functions.sql`
(функции).

### Route и Checkpoints

```text
position 0        СТАРТ      type 'start'
positions 1..N    чекпоинты  type 'checkpoint'   1 ≤ N ≤ 20
position N+1      ФИНИШ      type 'finish'
```

- Таблица `checkpoints (id, race_id, position, title, type, created_at)`:
  `UNIQUE (race_id, position)`, ровно один финиш, СТАРТ ⇔ позиция 0, название 1–60 символов.
- Маршрут задаёт учитель при создании гонки (`/create`: добавить, переименовать,
  ↑ ↓, удалить). `create_race(title, description, checkpoints text[])` принимает только
  названия по порядку — **позиции назначает база**. После создания маршрут неизменяем.
- Отложенный триггер при коммите проверяет, что маршрут непрерывный (0..N+1, финиш
  последний) — даже для прямых привилегированных записей. Гонка без маршрута не
  сохранится.
- Вызов `create_race` без маршрута (клиенты Этапа 1) даёт маршрут по умолчанию
  «Чекпоинт 1–3»; гонки, созданные до миграции, получили такой же.

### Team Position

- `teams.current_position` (0 = СТАРТ), `CHECK >= 0` и составной FK
  `(race_id, current_position) → checkpoints (race_id, position)`: позиция вне маршрута
  этой гонки невозможна на уровне базы.
- Единственный способ изменить позицию — `advance_team(team_id, to_position)`:
  - двигать может только студент этой команды (не учитель, не чужая команда);
  - только при статусе `running` (`race_not_started`, `race_finished`);
  - только `N → N+1` (`invalid_move` для `N+2`, назад, отрицательных); после финиша —
    `team_finished`;
  - повтор того же хода — ничего не делает (`moved: false`): двойной клик или ход
    товарища по команде не приводят к пропуску чекпоинта;
  - блокировки гонка → команда, как в функциях Этапа 1; членство проверяется под
    блокировкой гонки, поэтому переназначение студента не может проскочить между проверкой
    и ходом.
- Прямой `UPDATE teams.current_position` и любые записи в `checkpoints` запрещены (42501).

### Race Map и Realtime Movement

- `get_lobby()` теперь возвращает `route` и `teams[].position`: все участники видят
  маршрут и положение всех команд.
- Отдельного Realtime-механизма нет: ход обновляет `teams` → существующий триггер
  шлёт `lobby_changed` в `race:<id>` → клиенты перечитывают `get_lobby()` → карта
  обновляется.
- `/race/[raceId]` — экран гонки: у учителя карта, прогресс команд, «Завершить гонку»; у
  студента — своя команда, «Сейчас / Дальше», кнопка «Пройти чекпоинт N» (или
  «Финишировать»), карта с подсветкой своей команды. Лобби показывает маршрут и
  само переводит всех на карту при старте гонки.

## Этап 3: учебные задания на чекпоинтах

Миграции `20260929100000_checkpoint_tasks.sql` (схема) и
`20260929100100_checkpoint_task_functions.sql` (функции).

### Почему команда «альфа» оказалась на FINISH (исправлено)

Гонка `EGRN3D`: команда создана на СТАРТЕ, затем четыре отдельных хода `advance_team`
0 → 1 → 2 → 3 → 4 за 8 секунд (интервал ≈ время «запрос + перечитывание»). Пропусков
не было — на Этапе 2 «пройти чекпоинт» означало нажать кнопку, и повторные нажатия
проводили команду по всему маршруту. Теперь чекпоинт с заданием проходится только
правильным ответом; `advance_team` для него отвечает `task_required`. Воспроизведение —
`tests/db/progress-regression.test.ts`.

### Модель

- `checkpoint_tasks (id, race_id, checkpoint_id, type, question, options, sort_order,
  created_at)`: одно задание на чекпоинт (MVP, `UNIQUE (checkpoint_id)`), тип
  `single_choice` (2–6 вариантов) или `short_answer`, вопрос 1–500 символов.
- `private.checkpoint_task_keys (task_id, correct_option | correct_answer)` — правильные
  ответы в непубличной схеме: не видны через Data API и не выданы ни одной клиентской роли.
- `task_submissions` — каждый ответ: команда, задание, участник, текст ответа,
  правильность, время.
- `team_passes (team_id, position, passed_at)` — время прохождения каждой точки,
  включая ФИНИШ; первичный ключ не даёт записать проход дважды.
- Задания создаются вместе с гонкой: `create_race(title, description, checkpoints,
  tasks)`, по одному на каждый чекпоинт или ни одного (вызовы Этапов 1–2 и старые гонки
  работают как раньше — кнопкой).

### Как команда проходит чекпоинт

Команда на позиции `p` решает задание чекпоинта `p + 1`.
`submit_answer(team, task, answer)` проверяет: пользователь — студент этой команды,
гонка идёт (`running`), задание — именно следующего чекпоинта (`task_not_current` для
будущих), ответ корректного формата. Правильный ответ сдвигает команду на одну точку и
записывает проход; после последнего чекпоинта команда в той же транзакции попадает на
ФИНИШ. Неправильный — только записывается. Повторный ответ на уже пройденное задание
ничего не меняет (`alreadyPassed`). Короткие ответы сравниваются без учёта регистра,
лишних пробелов и ё/е.

### Защита правильных ответов

- Ключи лежат в `private`: схема не опубликована в Data API, у `anon` нет к ней доступа,
  а у `authenticated` (ему нужен `USAGE` для функций RLS) нет никаких прав на саму
  таблицу ключей.
- `get_lobby()` не читает ключи: студент получает только текущее задание своей
  команды (вопрос и варианты) и только во время гонки; учитель — вопросы без ответов.
  Прямой `SELECT` из `checkpoint_tasks` доступен только владельцу гонки.
- `submit_answer()` возвращает лишь вердикт `{correct, moved, alreadyPassed, position,
  finished}`.
- Realtime-сигналы — только `{table, op}`; ответы в них не попадают.

### Статистика и Realtime

`get_lobby()` учителю добавляет по каждой команде `stats`: число правильных и
неправильных ответов и время финиша. Новый ответ (`task_submissions`) и ход (`teams`)
вызывают `lobby_changed` в том же канале `race:<id>` — отдельного канала нет.

## Этап 4: очки и рейтинг

Миграции `20261007100000_scoring.sql` (схема) и `20261007100100_scoring_functions.sql`
(функции).

### Модель

- `task_submissions.points` — очки, которые принёс ответ: 100 + бонус за скорость
  (`50 − ⌊секунды / 3⌋`, не меньше 0) за верный, −20 за неверный. Бонус считается от
  момента, когда команда пришла на текущую точку (`team_passes.passed_at`; на старте —
  `races.started_at`).
- Счёт **не хранится** счётчиком: `private.team_standings(race)` считает его при чтении —
  `max(0, сумма очков ответов) + бонус финиша` (+100 / +60 / +30 по порядку прихода на
  ФИНИШ, при равном времени — по id). Поэтому две команды, финишировавшие одновременно,
  не могут получить один и тот же бонус, а клиенту нечего «подкрутить».
- Место: `rank()` по ключу «финишировал → время финиша → позиция ↓ → очки ↓»; равные команды
  делят место.

### Пауза после неверного ответа

`submit_answer` под той же блокировкой команды (`private.lock_member_team`) ищет последний
неверный ответ команды на это задание; если он был меньше 10 секунд назад —
`answer_cooldown`, попытка не записывается. Ответы напарников с других телефонов
выстраиваются в очередь на блокировке, поэтому паузу нельзя обойти параллельными
запросами. `get_lobby()` отдаёт студенту `currentTask.cooldownSeconds` — оставшиеся
секунды по часам сервера; клиент только показывает обратный отсчёт.

### Что видит кто

- `teams[].score`, `place`, `finishOrder` — всем участникам гонки (общая таблица).
- `teams[].stats` (верно / неверно / время финиша) — по-прежнему только учителю.
- Записать `points` или сдвинуть `submitted_at` напрямую нельзя (нет прав на UPDATE);
  `private.team_standings` клиентам не доступна.

## Этап 5: история гонки и аналитика

Миграция `20261008100000_race_report.sql` — одна функция, без новых таблиц и столбцов.

### get_race_report(race)

Security definer, только владелец гонки: чужая гонка, студент и несуществующий id получают
одинаковое `race_not_found`; `anon` не может вызвать функцию вовсе. Один запрос собирает
весь отчёт из уже существующих данных:

- `teams` — места и очки из `private.team_standings` (те же, что в лобби) плюс верные /
  неверные ответы и число участников;
- `tasks` — по каждому заданию: попытки, верные / неверные, сколько команд пробовали и
  прошли, сколько решили **первым ответом** (`distinct on (team_id)` по времени), среднее
  время от прихода на предыдущую точку (`team_passes`, для первой — `races.started_at`) до
  прохождения этой, топ-3 **неверных** ответов, сгруппированных `private.normalize_answer`
  (для выбора — текст варианта);
- `participants` — ученики с командой и их ответами;
- `timeline` — старт, ответы, финиши команд и конец гонки по времени; ответов — не больше
  2000 последних, чтобы ответ функции оставался небольшим.

### Секретность

Как и `get_lobby()`, отчёт не читает `private.checkpoint_task_keys`: в нём нет правильного
варианта и правильного текста — только счётчики, неверные ответы и «верно / неверно» в
хронологии. Тест `tests/db/report.test.ts` проверяет это на сериализованном JSON.

### Клиент

`lib/race/report.ts` проверяет форму ответа (`parseReport`), считает сводку и «трудные»
задания (решили первым ответом меньше 60 % команд) и строит CSV. Страница
`/race/[raceId]/results` — серверный компонент; время показывается в часовом поясе
браузера (на сервере — Asia/Bishkek до гидратации). CSV собирается в браузере из уже
загруженного отчёта, без отдельного запроса. Если миграция Этапа 5 не применена, страница
говорит об этом вместо «нет доступа».

## Границы безопасности

| Граница | Что защищает |
| --- | --- |
| Postgres-функции | Все решения о правах и состоянии гонки |
| RLS и права на столбцы | Прямой доступ через Data API: чтение только своего, запись запрещена |
| Триггеры и ограничения | Целостность даже при ошибке в коде функций или ручной правке |
| Приватный Realtime-канал | Получать события — только участникам, отправлять — только базе |
| Server Actions | Валидация ввода и понятные сообщения; повторно проверяют типы аргументов |
| `proxy.ts` / `getClaims()` | Актуальная и проверенная сессия на сервере |
| `safeNextPath()` | Редирект после входа только на пути этого сайта |

Секретный ключ Supabase приложению не нужен и нигде не используется.

## Тесты

- `tests/db/report.test.ts` — отчёт: доступ только владельцу, счётчики, первые попытки,
  время решения, группировка неверных ответов, отсутствие правильных ответов, хронология.
- `tests/report.test.ts` — разбор отчёта, сводка, «трудные» задания, CSV.
- `tests/db/scoring.test.ts` — очки, бонус за скорость, пауза, бонусы финиша, места,
  ничьи, видимость и обновление с Этапа 3.
- `tests/db/*` — миграции применяются к настоящему PostgreSQL (PGlite) с имитацией ролей
  Supabase ([`tests/db/supabase-shim.sql`](../tests/db/supabase-shim.sql)); атаки выполняются
  от ролей `authenticated` / `anon` с JWT-claims, как это делает PostgREST.
- `tests/*.test.ts` — валидация, статусы, ошибки, разбор снимка лобби.
- `tests/integration/*` — сценарии против настоящего Supabase-проекта, включая доставку
  Realtime (`npm run test:integration`). Учитель — заранее созданный подтверждённый
  тестовый аккаунт из `.env.test.local`, студенты — анонимные; регистраций по email и
  секретного ключа нет.
